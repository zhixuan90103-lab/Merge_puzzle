## 1. 原型成功标准（体验验收）

做完后，你应能在 `npm run dev` 下 **5 分钟内** 回答：

| # | 问题 | 合格信号 |
|---|------|----------|
| 1 | 拖是否好懂？ | 空位能挪；叠到同数会合；非法会弹回 |
| 2 | 「越合越满」是否成立？ | 合大块后更难塞；不是越玩越空 |
| 3 | 拖势定横竖是否有反馈？ | 横拖/竖拖出 2 或 8 的朝向可区分 |
| 4 | 紧张感有没有？ | 空位变少时决策变重（即使还没到 64） |
| 5 | 64 阀门感有没有？ | 至少 **调试入口** 或 **短路径** 能看到清空+重摆 |
| 6 | 失败是否清楚？ | 死局有提示；可重开 |

**不合格** 的典型结论（也有价值）：操作含糊 / 大块一出来就无解 / 到不了任何高潮 / 只有无聊搬家。

## 2. 范围：做 / 不做

### 2.1 必须做（P0）— 否则无法验玩法

| 模块 | 内容 | 规则依据 / 检索依据 |
|------|------|---------------------|
| 棋盘状态 | 8×8 占用表 + 块列表（id、value、占格/`w×h`+原点） | §3 §5 |
| **事务合并** | `tryMerge`：**克隆盘**上演算，成功才替换；失败零副作用 | R1 Sokoban unmove · R2 immutable |
| 形状 | 1/2/4/8 完整；16/32/64 能生成矩形即可 | §5.3 · R2 矩形并集仅作校验参考 |
| 拖拽输入 | **pointer capture** + `clientToDesign` → 格；松手 snap | §4 · R1 redblobgames |
| 搬家 | 整块脚印全空则提交 | §4.1 · polyomino |
| 合并 | 接触+同数；锚 B；先腾 A；可吃 A 旧格；拖势横竖 | §5 |
| 放不下弹回 | 选定朝向失败不改向 | §5.4 |
| 大推小（简版） | 新值严格更大；障碍 **整脚印**沿轴向平移；出界消灭；推不动整单失败 | §5.6 · R1 多格 Sokoban |
| 开局摆盘 | **手写固定一盘**；空位约 **≥40%**；存在可立刻合的一对 | R3 无硬公式→自定 |
| HUD | 状态 + **重开** + **Debug（升级选中 / 测试盘 / 接近 64）** | R3 jam debug |
| 失败检测 | 无合法合（双朝向 tryMerge）且无合法搬（全锚点脚印扫描） | §8 · R3 放置枚举 |

### 2.2 应做但可砍薄（P1）— 强烈建议有，否则验不全

| 模块 | 原型简化策略 |
|------|----------------|
| **64 清空 + 重摆** | 必须能触发；文案用 **「波次清空」** 非结束；主路径或 Debug |
| **出新块** | **仅合并成功后** 尝试出 **一个 1**；随机空 1×1；**出后仍非死局** 否则本次不出（严于经典 2048） |
| 平局拖势 | `\|dx\|≈\|dy\|` 双预演，优先能成功 / 空位更好 |
| **拖预览** | ghost 跟随；合法落点绿 / 非法红；松手非法回弹（chessground 思路） |
| **merge 纯逻辑单测** | 无 DOM：1+1 横竖、推失败回滚、吃 A 旧格（推荐） |

### 2.3 明确不做（P2 以后）

| 项 | 原因 |
|----|------|
| 行/列消除 | 规则已定不做 |
| 出块多种数字权重表 | 未定；1 足够验「越满」 |
| 开局/64 后两套不同生成 | 暂定同一套；原型手写盘即可 |
| 精美 3D、粒子、音效 | 干扰判断规则 |
| OrbitControls 绕场景转 | 与拖块冲突；原型关掉 |
| iOS 真机必验 | 桌面 dev 即可；震动非必须 |
| 计分/关卡编辑器 | 非验证核心 |

### 3.1 直接复用

| 能力 | 位置 | 原型用法 |
|------|------|----------|

| haptics | `utils/haptics.ts` | 可选：合并成功轻震 |

### 3.2 须改 / 须避

| 点 | 说明 |
|----|------|
| `main.ts` demo | 紫立方体 + **OrbitControls** 与拖块抢输入 → **拆掉或隔离** |
| `canvas` pointer | demo 把 canvas `pointerEvents = auto` 给 orbit；玩法要在 **stage 上统一收 pointer** |
| 无 `src/game` | 全部新建 |

### 3.3 技术选型（原型推荐）

为 **最快可玩**，推荐：

| 层 | 推荐 | 理由 |
|----|------|------|
| 逻辑 | 纯 TS，无 Three 依赖 | 可单测合并/推 |
| 表现 | **DOM 或 2D Canvas** 画在 `#stage` 内（设计坐标） | 格子游戏不需要 3D；省相机/射线 |
| 备选 | Three 正交相机 + 平面 mesh | 与现 WebGPU 一致，但拖拽映射更慢 |

**计划默认：逻辑 `src/game` + 视图 `BoardView`（DOM/CSS grid 或 canvas 2d）。**  
WebGPU 启动链可保留作壳（或暂不创建 renderer，仅 stage+UI）——若去掉 renderer，须确认 `createRenderer` 失败路径不挡 dev；更稳是 **仍 boot renderer 但不交互**，棋盘用 DOM 盖在 stage 上。

更干净的一刀：

> 原型 boot：**保留** adapt/layout/safeArea；**不强制** Three 场景；`#stage` 内挂 `#board-root`（绝对定位铺满 stage）接收拖拽。

## 4. 模块拆分与文件计划

```
src/game/
  types.ts          # Piece, Cell, BoardState, Orientation
  shapes.ts         # value → 候选矩形 (w,h)；占格枚举
  board.ts          # 占用图、放置/移除、克隆
  merge.ts          # 拖势、生成新脚印、推、提交/回滚
  move.ts           # 合法搬家脚印
  deadlock.ts       # 是否存在合法合/搬
  spawn.ts          # 原型：合并后尝试放一个 1
  deal.ts           # 固定开局 + 64 后同一套（或同一函数）
  input.ts          # pointer → 选中/拖/松手
  view.ts           # 渲染块与高亮
  game.ts           # 状态机：idle/drag、64、fail、restart
  debug.ts          # 可选：跳到高占用盘、强制值
src/main.ts         # boot 壳 + initGame()
```

依赖方向（单向）：

```
types/shapes → board → merge/move/deadlock/spawn/deal
                ↑
              game ← input/view
main → game
```

## 5. 分阶段实现（检索后的施工顺序）

### Phase 0 — 壳（0.5d 量级）

- [ ] `main.ts`：去掉 Orbit + demo mesh（或条件开关）  
- [ ] `#stage` 内建立 board 容器（设计坐标 满 stage 或居中方形棋盘区）  
- [ ] `#ui-root`：状态一行 +「重开」  
- [ ] 验证：手机/Pad 预览下点击坐标能打出 design 与格索引  

**检查点：** 点哪一格，log 出正确 `(gx,gy)`。

### Phase 1 — 静态盘 + 搬家

- [ ] `types` / `shapes` / `board`  
- [ ] 固定开局（见 §6）渲染色块+数字  
- [ ] 拖到空脚印 → 搬家；非法弹回  
- [ ] 多格块（先有 2 或 4）整块拖  

**检查点：** 只挪不合也手感清楚。

### Phase 2 — 合并核心（玩法验票点）

- [ ] 接触检测 + 同数  
- [ ] 拖势横/竖；平局简规则  
- [ ] 先腾 A、吃 A 旧格、标准形状  
- [ ] 失败弹回  
- [ ] **尚无推**：目标格被占则直接失败（先跑通无障碍合）  

**检查点：** 1+1→2、2+2→4、4+4→8 朝向可跟手。

### Phase 3 — 大推小 + 死局

- [ ] 新值严格更大才推；推出界删除  
- [ ] 推不动整次回滚  
- [ ] `deadlock` + UI「走不动了」+ 重开  

**检查点：** 用小块挡大合并时，能推走或正确失败。

### Phase 4 — 越满 + 64 阀门

- [ ] 合并成功后 `spawn` 一个 1（安全位）  
- [ ] 64 检测 → 清盘 → `deal()` 再摆  
- [ ] Debug：一键加载「易出 8/16」盘或升级选中块，保证能看到 64 清盘  

**检查点：** 完整体验「变堵 →（调试）64 → 清空再来」。

### Phase 5 — 体验打磨（仍属原型）

- [ ] 合法落点高亮 / 可合并描边  
- [ ] 合并成功短反馈（色闪或 haptics.tap）  
- [ ] 状态字：块数、空格数、最近操作结果  

**检查点：** 外人不用讲解能玩 2 分钟。

## 6. 原型开局盘（建议手写，保证可复现）

目标：开局 **有空位**、能立刻合、能感到会变堵。

示例原则（实现时可微调坐标）：

- 约 **12～20** 个值为 1 的块 + **2～4** 个值为 2 的块  
- 空位约 **40%+**，避免满盘假死  
- 至少两对 1 相邻或可轻松叠合  
- **不要** 开局总和逼近 64 还无空（规则推演已证会卡）

64 后重摆：调用 **同一 `deal()`**（暂定 C）。

Debug 盘（可选第二套）：

- 多个 8/16 半成品，便于 10 次操作内摸到 64 清空。

## 7. 合并算法最小实现契约（防走偏）

与 GAME_RULES §5.5 对齐的函数级契约：

```ts
// 伪接口，非最终代码
tryMerge(board, pieceAId, pieceBId, dragDx, dragDy): 
  | { ok: true; board: BoardState; createdValue: number }
  | { ok: false; reason: 'orient' | 'blocked' | 'push' }
```

顺序硬约束：

1. `valueA === valueB` 且 footprints 接触  
2. 移除 A → 算 orientation → 算 newCells  
3. newCells 可含 A 旧格  
4. 对其余冲突：`2V > other` 则沿扩展方向推，否则 fail  
5. 提交；`createdValue===64` 则 clear + deal  

原型可先 **不做 BFS 连环推**：只推「新脚印内的障碍」各一次平移尝试。

## 13. 修订后施工顺序（检索后定稿）

相对初版 Phase，**插入事务与预览，Debug 提前**：

| 阶段 | 内容 | 完成标准 |
|------|------|----------|
| **0 壳** | 去 Orbit/demo 抢输入；stage 内 board 区；`clientToDesign`→格 log；HUD 重开 | 点哪格对哪格 |

**架构不变**：纯 TS 逻辑 + DOM/Canvas 2D 视图（推荐）。

**一句话定稿：**

> 原型 = **克隆事务棋盘** + **脚印拖放/推动** + **合后安全出 1** + **64 波次清空** + **Debug 保验收**；规则细节以 `GAME_RULES.md` 为准，外部只借通用手法。

## 14. 自洽评估与执行就绪（Go / No-Go）

评估对象：`GAME_RULES.md` v0.1 + 本计划 §1–§13 + 底座能力。  
目标：是否可进入 **原型执行阶段**（非上线成品）。

### 14.1 总裁决

| 项 | 结论 |
|----|------|
| **是否可执行原型** | **有条件通过（Conditional Go）** |
| 可开阶段 | **Phase 0 → 4**（体验验收包） |
| 不可声称 | 完整数值/出块表/连环推终稿已齐 |
| 阻塞等级 | **无 P0 级逻辑自相矛盾**；余下为可冻结的实现约定 |

**一句话：**

|---|------|------|------------|
| A | 合不腾空 + 合后出块 → 密度单调升 | 设计意图 | 用体验验「堵是否好玩」 |
| B | 隔空合可能偏强 | 体验风险 | 先按规则做；不合格再加相邻开关 |
| C | 推出界减质量，不利自然摸 64 | 体验风险 | Debug 盘；推可保留当清障 |
| D | `GAME_RULES` 出块时机 **未定** vs 计划「仅合并后」 | 文档落差 | **原型冻结** 为仅合并后，回写备忘 |
| E | 形状「以 B 为锚生成」缺角点公式 | 实现细节 | §14.4 冻结锚点算法 |
| F | 连环推未终稿 | 细节 | 原型 **单步脚印推** |
| G | 死局全量 tryMerge 成本 | 性能 | 8×8 + 少块可接受 |
| H | 拖起时 A 是否仍占格 | 交互歧义 | §14.4 冻结：拖起后逻辑上腾空，失败还原 |

### 14.4 执行冻结（开工即采用，不另开设计会）

下列在原型期内视为 **已定实现**（可逆，但改则同步文档）：

| ID | 冻结内容 |
|----|----------|
| F1 | **表现**：DOM/CSS 棋盘在 `#stage` 内；可保留 WebGPU 壳但不交互 |
| F2 | **出块**：仅 `merge` 成功后尝试放 **一个 value=1**；出后 `!deadlock` 否则跳过 |
| F3 | **拖起**：pointerdown 选中后，逻辑盘 **暂时移除 A 占格**（幽灵绘制）；弹回则写回 |
| F4 | **接触**：松手时幽灵脚印与 B 脚印至少一格相交（或 4-邻接，二选一写进代码常量，默认 **相交或边邻**） |
| F5 | **新矩形锚法**：目标 `w×h` 由值+朝向决定；放置使 **与 B 旧脚印重叠格数最大**，再沿拖势主轴对齐；仍非法则 fail |
| F6 | **推**：新脚印内每个障碍整块沿主轴平移；目标格全空或出界（出界=删）；任一块无法安置则整单 fail；**不做连环多段 BFS** |
| F7 | **deal**：同一手写函数生成开局与 64 后；另备 Debug 密盘 |
| F8 | **判序**：merge 成功 → if 64 then clear+deal → else spawn 尝试 → deadlock 检查 |
